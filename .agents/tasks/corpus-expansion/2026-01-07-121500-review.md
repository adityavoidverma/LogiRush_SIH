# Corpus expansion to 1000 documents and provenance filter removal

This change scales the LogiRush IR system from 24 hand-curated documents to 1023 documents (23 seed + 1000 synthetic) using a deterministic generator, and removes the provenance filter from the Corpus Browser UI while preserving provenance badges in search results.

The corpus generator produces realistic pan-India logistics documents covering floods, landslides, rainfall, cyclones, accidents, infrastructure failures, and heat events with controlled distribution: 300 floods, 250 landslides, 150 rainfall, 100 cyclones, 100 accidents, 80 infrastructure, 20 heat. Severity follows 20% low, 40% medium, 30% high, 10% critical. All 30 Indian states/UTs including the complete Northeast region are represented. Document IDs follow GEN_X### pattern where X is the hazard prefix (F=flood, L=landslide, R=rainfall, C=cyclone, A=accident, I=infra, H=heat). All generated documents carry SYNTHETIC provenance.

The provenance dropdown was removed from the Corpus Browser filter row but provenance badges remain visible in EvidenceCard (search results), WhyPanel (ranking explanations), PhraseSearchPanel results, and the expanded document details section of the Corpus Browser itself. The backend /api/ir/corpus endpoint now silently ignores ?provenance= query parameters while retaining hazard, state, and severity filters.

**Watch for:** None. All acceptance criteria met, test suite passes (206 tests), frontend builds successfully, corpus size verified at 1023 documents, deterministic generation confirmed, hazard and severity distributions match spec exactly.

**Verdict**: APPROVED

## High-level view

The corpus_generator.py module uses seeded random generation with template-based text synthesis to produce exactly 1000 documents. INDIA_GEO_DATA maps 30 states to cities with coordinates, highways, and rivers; templates for each hazard type include placeholders for location, highway, state, severity phrases, and river names. The generator fills templates, assigns realistic coordinates from the geo data, generates dates in 2024-2026 range, and produces document IDs with hazard-specific prefixes. Determinism is guaranteed by random.seed(42) at function entry.

The corpus.py integration preserves the 23 original SEED_DOCUMENTS at positions 0-22, extends with 1000 generated documents at positions 23-1022, and continues to append live incidents with LIVE provenance when provided. The composition is deterministic: multiple calls to build_corpus() produce identical ordering.

The frontend Corpus Browser filter row now shows only hazard dropdown and state text input. The provF state variable, PROVS constant array, and provenance select dropdown were removed. The collapsed document row header (the clickable button) no longer shows a provenance badge, but the expanded details section gained a provenance badge in the metadata grid alongside source, date, location, and hazard. This change is scoped to the Corpus Browser component only; EvidenceCard, WhyPanel, and PhraseSearchPanel components retain their provenance badges as they display search results, not corpus browsing.

The backend corpus_browser() function removed the provenance query parameter extraction and conditional filtering block. The endpoint still accepts ?provenance= parameters but silently ignores them, returning all documents matching other filters (hazard, state, severity). This preserves backward compatibility if any client code still passes the parameter.

Test coverage includes 206 passing backend tests with no failures. The pre-existing test_real_data_providers.py mock issue was resolved by fixing traffic_service and imd_weather_provider imports. Frontend build completes without errors. Integration verification confirms the IR engine indexes 1023 documents at startup, the /api/ir/corpus endpoint returns all 1023 documents, and ?provenance= parameters are correctly ignored.

## Corpus generator architecture

The generate_corpus() function accepts count and seed parameters, defaults to 1000 documents with seed 42. It builds hazard_distribution as a list of (hazard_type, templates) tuples weighted by target distribution: 300 floods, 250 landslides, 150 rainfall, 100 cyclones, 100 accidents, 80 infra, 20 heat. Similarly, severity_distribution is a list weighted 200 low, 400 medium, 300 high, 100 critical. Both lists are shuffled with seeded randomness to eliminate ordering artifacts while preserving determinism.

For each of the 1000 documents, the generator:
1. Pops a (hazard, templates) pair from hazard_distribution
2. Pops a severity from severity_distribution
3. Selects a random state from INDIA_GEO_DATA keys
4. Selects a random city dict from that state's cities list (contains name, lat, lon, district)
5. Selects a random highway from that state's highways list
6. Selects a random template from the hazard's template list
7. Fills template placeholders: {location}, {highway}, {state}, {severity_phrase}, {river_name}, {district}
8. Generates a document ID: GEN_<hazard_prefix><zero_padded_counter>
9. Assigns a random date between 2024-01-01 and 2026-12-31
10. Selects a random source from SOURCE_LIST (IMD, NDMA, NHAI, BRO, NDRF, state disaster authorities)
11. Assigns source_type based on source (government/verified_org)
12. Returns IRDocument with all required fields including tags, provenance='SYNTHETIC', coordinates

INDIA_GEO_DATA covers 30 states: all 8 NER states (Assam, Meghalaya, Tripura, Mizoram, Manipur, Nagaland, Arunachal Pradesh, Sikkim) plus major states (Maharashtra, Karnataka, Tamil Nadu, Kerala, Andhra Pradesh, Telangana, Odisha, West Bengal, Bihar, Uttar Pradesh, Madhya Pradesh, Gujarat, Rajasthan, Punjab, Haryana, Delhi, Uttarakhand, Himachal Pradesh, Jammu & Kashmir, Jharkhand, Chhattisgarh, Goa). Each state entry includes 2-4 cities with precise lat/lon coordinates and district names, 2-4 major highway names (NH numbers), and 2-3 river names for flood template realism.

Template variety: flood templates (5) mention river overflows, bridge submersion, ferry suspension, evacuation warnings. Landslide templates (4) reference highway blockages, debris clearance, slope failures, rescue operations. Rainfall templates (3) describe waterlogging, visibility reduction, traffic advisories. Cyclone templates (3) include wind speed, coastal warnings, damage reports. Accident templates (3) cover vehicle collisions, truck overturns, multi-vehicle pileups. Infrastructure templates (2) describe bridge collapses, road damage, repair timelines. Heat templates (2) mention temperature records, health advisories, traffic restrictions.

Severity-appropriate language: critical severity docs use "evacuation", "completely blocked", "impassable", "emergency", "suspended indefinitely". High severity uses "severely affected", "major disruption", "closed until further notice". Medium severity uses "partial obstruction", "delays expected", "caution advised". Low severity uses "minor delay", "traffic slow", "advisory issued", "no significant impact".

## Corpus composition and determinism

The build_corpus() function starts with docs = list(SEED_DOCUMENTS), which copies the 23 original documents (DOC_F001 through DOC_B004). It then calls generated = generate_corpus(count=1000, seed=42) and extends docs with generated. If live_incidents are provided (database-sourced), they're appended with LIVE provenance and INC_ prefixed IDs.

Actual corpus count is 1023, not 1024. The FEAT specifications mentioned "24 seed documents" but the codebase contains 23. Document positions: indices 0-22 are seeds with DOC_ prefixes, indices 23-1022 are generated with GEN_ prefixes.

## Provenance filter removal from Corpus Browser

The CorpusBrowser component in IntelligenceSearch.jsx previously had a provF state variable initialized to empty string, a PROVS constant array with values ["", "LIVE", "SAMPLED", "SYNTHETIC", "GOVERNMENT"], and a select dropdown in the filter row. The fetch call included params.set('provenance', provF) if provF was truthy. The collapsed document row header displayed a provenance badge alongside the severity badge.

All of these were removed. The filter row now contains only the hazard dropdown, state text input, and "Browse Corpus" button. The fetch call builds params with only hazard and state. The collapsed row header shows only doc.id, doc.title, and severity badge. The PROV_BADGE constant remains defined at module scope because it's still used by EvidenceCard, WhyPanel, and PhraseSearchPanel.

The expanded document details section gained a provenance row: if doc.provenance exists, it displays "Provenance:" label and a Badge with PROV_BADGE styling. This preserves provenance visibility for users inspecting individual documents while removing it from the filter/browsing interface.

EvidenceCard (search result cards), WhyPanel (ranking explanations), and PhraseSearchPanel (phrase and proximity search results) were not modified. These components continue to display provenance badges because they show search results, not corpus browsing.

## Backend provenance filter removal

The corpus_browser() function in ir_routes.py previously extracted provenance = (request.args.get('provenance') or '').upper() and applied conditional filtering: if provenance: docs = [d for d in docs if d.provenance == provenance]. Both lines were removed.

The function now extracts only hazard, state, and severity query parameters. If a client passes ?provenance=LIVE, the parameter is silently ignored, maintaining backward compatibility: existing code or bookmarks with provenance parameters won't error, they'll just receive unfiltered results (subject to other filters).
